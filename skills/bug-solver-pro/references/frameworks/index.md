# Framework and library index

Identify the installed dependency and failing boundary, then start with its local playbook. Each module has concrete symptom → mechanism → probe/falsifier → repair/verification recipes in its own directory.

Use the guide to expand beyond the recipes. Follow the [documentation access workflow](../framework-documentation.md) when an API contract, version difference, or configuration is unresolved. Official docs support the techniques rather than replace local investigation.

Every current module also has a deeper `boundary-case.md`, linked from its playbook and indexed in the [coverage audit](../coverage/gap-audit.md). The CLI can print both local resources with `search.py "<symptom>" --framework "<name>" --plan`. For interpretation, use [causal decision gates](../19-causal-decision-procedure.md) and [composed failures](../20-composed-failures.md); an untriggered probe is inconclusive.

React, Vue, and Svelte are included for state/rendering boundaries even when described as libraries or compilers. Combine them with the relevant application framework module when the failing flow crosses both.

For an unlisted framework, inspect its actual implementation path using [stack semantics](../14-stack-semantics.md), researching an unresolved contract from official package metadata/repositories when needed. Do not substitute a neighboring framework's behavior. Use the [module template](../../templates/stack-module.md) to extend coverage; link a new module here, in the [language index](../languages/index.md), and in its parent guide. Include a populated local playbook and documentation map; a URL list alone is insufficient.
